## Установка согласованных версий с выключенным приёмом

1. После отдельного разрешения сохранить копию кода/конфигурации существующих ресурсов. Не сохранять секреты в Git или отчёт. Не сбрасывать существующие Script Properties.
2. Сначала заменить существующий Apps Script полным backend/Code.gs. При MYPAGE_ENABLED=false и MYPAGE_NOTIFICATIONS_ENABLED=false выполнить installClosedLaunchSettings: он выставит версию mypage-privacy-2026-11-04-v1 и закрытые флаги, не удаляя остальные свойства. Затем setupPrivacyMaintenance: создаст только отдельный MypagePrivacyV1 (10 столбцов метаданных); Лист1 A:G и журнал A:M не расширяет и не очищает. Обновить существующее /exec через Управление развёртываниями → Новая версия.
3. `node tools/check_launch.mjs` проверяет согласованность локальной версии/флагов/ресурсов/шрифтов. `node tools/closed-install.mjs` без аргументов печатает только план, не использует сеть.
4. Только после разрешения облачной установки и фактической проверки Apps Script: `node tools/closed-install.mjs --allow-cloud-install --apps-script-installed`. Нужен установленный официальный wrangler и обычная авторизация владельца. Скрипт не принимает секретов в аргументах. Он применяет CREATE IF NOT EXISTS из schema.sql (добавляет erasures/индекс, не удаляет данные), затем устанавливает Worker из backend/wrangler.production.toml в существующий аккаунт/Worker/DB. Флаг apps-script-installed — явное подтверждение оператора, не автоматическая проверка облачного исходника.
5. Конфиг закрывает приём, обновляет только публичные переменные и задаёт реальное расписание: `0 3 * * *` — ежедневная D1-очистка; `0 * * * *` — почасовой мост удаления и ранняя очистка Telegram. Время UTC, в Варшаве зимой +1, летом +2. В 03:00 это два независимых события, обработчик разделяет их по cron. Подготовлены custom logs с конечными кодами, invocation_logs=false для минимизации метаданных запроса. Это не удаляет собственные security-данные провайдера. Секреты Wrangler deployment не удаляет; secrets-file/secret bulk не используются. Не использовать keep-vars для сохранения старой версии политики поверх утверждённой; после установки сверить все переменные/привязки с планом.
6. В Cloudflare → Worker ivan-praca-leads → Settings → Trigger events → Cron triggers проверить ОБА выражения. Подождать распространения изменений (официальная документация допускает до 15 минут). На очередном плановом событии при выключенных флагах проверить Invocation/Metrics; own event MAINTENANCE с disabled=true появляется, если для кода разрешены доступные журналы. Сверить, что счётчики таблиц не изменились. Не нажимать принудительный purge и не тестировать реальными данными. Без этой облачной проверки расписание не объявлять действующим.
7. Только после отдельного разрешения на удаление: проверить фактическое окно D1 Time Travel, отсутствие PREPARED/конфликтов, наличие MypagePrivacyV1 и согласованные исключения. В Apps Script → Настройки проекта → Свойства скрипта поставить MYPAGE_RETENTION_ENABLED=true. В Cloudflare → Worker → Settings → Variables and Secrets поставить RETENTION_BRIDGE_ENABLED=true и D1_CLEANUP_ENABLED=true. Не добавлять отдельный триггер Apps Script: почасовой Worker вызывает подписанный /exec, ежедневный cron обслуживает D1. MYPAGE_TELEGRAM_DELETE_ENABLED и MYPAGE_NOTIFICATIONS_ENABLED оставить false; приём не включать. Проверить плановые вызовы по журналам и результаты по агрегатам, без принудительного запуска. Эти флаги могут удалить уже просроченные данные при ближайшем cron. Для остановки вернуть все три флага обслуживания в false.

## Как удаляются рабочие копии

- Срок рассчитывается как шесть календарных месяцев UTC с корректным концом месяца/високосным годом. Плановая очистка начинает выборку за 24 часа до границы; исправный почасовой процесс даёт запас, а не обещание удаления при любом отказе.
- До 20 подходящих записей за вызов, без физического удаления/сдвига строк. Неистёкшие и недавно завершённые записи пропускаются. При backlog/ошибках до истечения срока требуется вмешательство владельца; одной настройки cron недостаточно для гарантии срока. Следить за MAINTENANCE_FAILED и состояниями ledger, квотами Apps/Worker/D1. Не заменять это новым платным сервисом.
- Под ScriptLock проверяются PREPARED, уникальность UUID и источник строки. PREPARED/конфликт останавливает обработку без очистки кандидата. MYPAGE_LEGAL_HOLD_IDS — JSON-массив UUID, удерживаемых только на отдельном действительном основании; основание/срок владелец документирует вне общедоступных логов. Само помещение в список не создаёт правового основания.
- Перед стиранием ставится ERASING, затем очищаются A:G и base64/контактные данные A:M. Остаётся короткий UUID-маркер ERASED. Сбой между шагами не создаёт заявку заново: восстановление записи и приём повторного UUID заблокированы.
- Apps возвращает подписанный manifest с UUID, nonce и временем. Worker проверяет HMAC, протокол и свежесть, атомарно добавляет короткий erasure-маркер D1 и удаляет только квитанции указанных UUID, проверяет отсутствие и подписанно подтверждает Apps. При сбое D1/ack процесс повторяется как удаление, а не как отправка заявки. Токены Turnstile и /applications не используются.
- После завершения сверки краткосрочные метаданные очищаются через 7 дней. Это маркеры безопасности по 6(1)(f), не поля заявки. Срок согласован с подтверждённым Free-окном D1 Time Travel; при Paid/других backup-окнах до включения нужен пересмотр защиты от восстановления.
- Ежедневная D1-очистка независимо удаляет истёкшие rate-limit записи, квитанции старше 7 суток и истёкшие erasure-маркеры. В этом PR активные облачные записи не тронуты.

## Отзыв согласия / запрос удаления

Получить обращение на ivanz.astarta@gmail.com, соразмерно проверить личность и найти все относящиеся UUID/Meta-заявки/выгрузки; не требовать паспорт по умолчанию. Немедленно прекратить контакт на основании отозванного согласия. Проверить, действительно ли есть другое основание, не вводить бессрочный hold по умолчанию.

Владелец в Script Properties указывает MYPAGE_ERASE_REQUEST_ID и MYPAGE_ERASE_REASON (withdrawal или erasure), затем выбирает queueOwnerPrivacyRequest. Это только защищённая операторская постановка в очередь, не публичный endpoint удаления. При включённом отдельно обслуживании ближайший tick сотрёт рабочие данные; до него новые уведомления по этой записи блокируются. При выключенном обслуживании очередь остаётся очередью: нельзя отвечать заявителю «удалено». Для нескольких UUID повторить операторское действие, фиксируя объём запроса приватно.

Проверить итог: поля отсутствуют в обеих Google-вкладках, D1 receipt отсутствует, Telegram/экспорты/история проверены; минимальные временные маркеры отдельно объяснить при запросе. Обычно ответ заявителю — до месяца; причины законного продления/сохранения объясняет владелец. Не подтверждать стирание всех backup по одной очистке диапазона.

## Telegram: раннее удаление и ручной предел

Новая версия уведомлений содержит только UUID. До sendMessage в MypagePrivacyV1 сохраняется unknown, после подтверждения — message_id и время. Через 24 часа обслуживания код может вызвать только deleteMessage, если отдельно разрешён MYPAGE_TELEGRAM_DELETE_ENABLED. Это разрешение не включает sendMessage и действует независимо от MYPAGE_NOTIFICATIONS_ENABLED=false.

Bot API не позволяет универсальное удаление сообщений через шесть месяцев: предел deleteMessage — меньше 48 часов. При неизвестном message_id, возрасте >=48 часов, отказе/тайм-ауте удаления состояние помечается для владельца, а не объявляется удалённым. Чтобы закрыть и окно неизвестной доставки, до разрешения уведомлений настроить и проверить доступное автоудаление группы не дольше суток. Настройку и удаление старых сообщений владелец подтверждает отдельно; бот/разработка этого не выполняли.

После фактического удаления в обычном Telegram UI владелец задаёт UUID в MYPAGE_ERASE_REQUEST_ID и MYPAGE_CONFIRM_TELEGRAM_DELETION=true, выполняет confirmOwnerTelegramDeletion. Это явная аттестация владельца, не доказательство Bot API; флаг сбрасывается в false. Не использовать её без проверки сообщения. Предыдущие уведомления старого кода могли содержать поля заявки, а не только UUID: проверить их вручную.

## Google history, копии, Meta и восстановление

clearContent не чистит историю версий. Доступность удаления истории в интерфейсе этого аккаунта не подтверждена. Если действие доступно, оно необратимо и требует отдельного разрешения. Именованные версии/локальные экспорты/другие копии требуют отдельного учёта. Никаких API-обещаний «вся история удалена»: Drive revisions.delete для native Sheets этого не даёт. При недоступности подходящей очистки истории согласовать с владельцем другой процесс/хранилище; не уничтожать рабочую таблицу ради теста.

Строки Лист1 без UUID-записи в MypageJournalV2 не удаляются автоматически: нельзя приписать им чужое согласие/идентификатор. Владелец отдельно проверяет их источник, дату и срок; исходную существующую строку эта разработка не меняет.

Meta-формы и копии вне MypageJournalV2 не попадают в автоматическую выборку: владелец находит и удаляет их через доступные инструменты Meta/экспортов. Не утверждать их очистку этим скриптом. При восстановлении Google/D1/локального backup сначала заблокировать приём, сверить период восстановления с журналом удалений и повторно применить согласованные удаления до возвращения доступа. Приватный реестр действий и правовых исключений ведётся с минимальным содержимым и собственным сроком; не сохранять там копию удалённых контактов.

## Остановка и откат

Остановить без удаления: Worker D1_CLEANUP_ENABLED=false, RETENTION_BRIDGE_ENABLED=false; Apps MYPAGE_RETENTION_ENABLED=false, MYPAGE_TELEGRAM_DELETE_ENABLED=false. Приём/уведомления остаются false. Проверить сохранение флагов. Код откатить при закрытых flags; не откатывать очищенные данные из backup как «обычный rollback». Не удалять ledger/erasures во время незавершённой операции. Автоматического административного watchdog нет.
