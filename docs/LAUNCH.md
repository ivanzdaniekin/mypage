1. Сохранить резервную копию кода и параметров существующего развёртывания, не копируя секреты в Git/чат.
2. Проверить закрытые флаги: Worker ENABLED=false, PRIVACY_APPROVED=false, TEST_ONLY=true; Apps MYPAGE_ENABLED=false, MYPAGE_NOTIFICATIONS_ENABLED=false, MYPAGE_ALLOW_PROBE=false. Не менять ключи.
3. В существующем Apps Script заменить код целиком backend/Code.gs, сохранить. Обновить существующее развёртывание: Развернуть → Управление развёртываниями → карандаш → Новая версия → Развернуть. Сохранить существующий /exec, доступ и идентификатор. Не создавать новое развёртывание и не выполнять setupMypage повторно: журнал уже существует.
4. Только затем установить backend/worker.mjs в существующий ivan-praca-leads, сохранив секреты, D1 binding DB и закрытые флаги. Новому Worker нужны подписанные подтверждения нового Code.gs; старый Apps Script не совместим с этим требованием. Worker старой версии допускает дополнительные поля ответа, поэтому обновление Apps первым безопаснее; при откате учитывать ту же совместимость.
5. Проверить соответствие кода/версий без заявок. Статическая проверка не заменяет приёмку живого сервиса. Новые live-заявки или запросы статуса требуют отдельного разрешения; без него использовать только offline-тесты.

## 3. Сохранение, подтверждения и повторные идентификаторы

Worker сначала проверяет Origin/CORS, TEST_ONLY и TEST_KEY, закрытые флаги, размер/поля/согласие, ограничения частоты и настоящий Turnstile (hostname ivanzdaniekin.github.io, action candidate). TEST_KEY никогда не нужен публичному браузеру: пока TEST_ONLY=true, рабочая публичная форма не запускается.

Worker подписывает тело timestamp + '.' + payload. Apps Script проверяет подпись и допустимый возраст; заголовки doPost(e) для авторизации не используются. Запись PREPARED резервирует фиксированную строку, после записи и flush журнал становится SAVED. Ответ содержит confirmation.payload и HMAC от 'save.'+payload. Worker проверяет протокол, UUID, digest полей, подпись и время, затем выполняет условный UPDATE receipts с RETURNING id,saved. Только совпавшая возвращённая строка даёт браузеру saved=true.

Google ContentService может вернуть 301/302/303: разрешён один HTTPS-переход только на script.googleusercontent.com, выполняемый GET без тела и подписанных данных. Другой redirect, отрицательный HTTP, JSON >16 KiB, повреждённая или неподписанная квитанция не подтверждают сохранение. Коды APPS_POST_TRANSPORT/APPS_REDIRECT_TARGET/APPS_CONTENT_TRANSPORT/APPS_HTTP/APPS_JSON/APPS_RECEIPT/APPS_SIGNATURE/D1_CONFIRM различимы без вывода исключений, URL, токенов и полей кандидата. Служебные invocation-логи провайдера имеют собственные настройки и могут содержать IP; доступ/сроки нужно ограничить отдельно.

Повтор того же UUID с тем же содержимым использует существующую квитанцию/фиксированную строку. Изменённые поля с тем же UUID — конфликт. Совпадающая заявка с другим UUID в пределах окна дедупликации получает DUPLICATE, а не ложное подтверждение несуществующего UUID. Turnstile остаётся обязательным и не переиспользуется. При неизвестном результате клиент не делает автоматических повторов; форма блокирует повторную отправку и показывает UUID для сверки. Процедура отдельного read-only восстановления — docs/CONFIRMATION-RECOVERY.md; не помечать saved=1 по одному HTTP 200.

Лист1 A:G: дата/время | имя | телефон/Telegram | город | работа | `mypage / UUID` | Новая. Пользовательский текст записывается как literal text. Журнал MypageJournalV2 содержит request_id, digest, fingerprint, created, target_row, payload_b64, consent_at, privacy_version, state, telegram_status, attempts, next_attempt, last_code. Base64 не шифрование. consent_at — серверное время получения согласия. Любые сторонние writers должны соблюдать блокировку; нельзя физически сортировать/удалять строки при PREPARED.

## 4. Telegram: один существующий синтетический тест — пока НЕ запускать

Подготовлена notifyExistingSyntheticOnce, жёстко ограниченная UUID `f20b1b0c-887a-43d4-b671-5a303d09ffc0`. Она не вызывает saveLead или общий retryTelegram, не меняет Лист1, не отправляет чужие ожидающие уведомления. Под ScriptLock проверяет единственность UUID, SAVED, неизменность строки и синтетических полей, pending/attempts=0, отсутствие других pending/needs_review/PREPARED/IN_FLIGHT и конфигурацию группы.

После отдельного разрешения на установку нового Code.gs и одно сообщение:
1. Убедиться, что нет активного Telegram-триггера; приём Worker/Apps остаётся выключенным, MYPAGE_ALLOW_PROBE=false.
2. Временно разрешить MYPAGE_ALLOW_SYNTHETIC_NOTIFICATION=true и MYPAGE_NOTIFICATIONS_ENABLED=true.
3. В редакторе выбрать только notifyExistingSyntheticOnce и выполнить один раз. Не выбирать retryTelegram.
4. Сразу вернуть оба флага false независимо от результата. Сверить сообщение с UUID и журнал. Не перезапускать при ошибке/тайм-ауте.

Перед сетевым вызовом в журнале устойчиво сохраняется needs_review + IN_FLIGHT + номер попытки. Успех Telegram с message_id переводит запись в sent. При неопределённом результате автоматического повтора нет. Даже если Telegram принял сообщение, а фиксация sent не удалась, очередь не отправит его повторно. Абсолютную exactly-once доставку Telegram API без идемпотентного ключа обеспечить нельзя; в спорных случаях нужна ручная сверка сообщения, а не сброс attempts.

Общий retryTelegram разрешён только для будущей утверждённой эксплуатации: максимум 5 сообщений за вызов и 10 попыток на запись, ScriptLock, экспоненциальная задержка от 5 минут до суток. Автоматический повтор только при явном отказе 429 с ok=false и учётом retry_after; сетевой сбой, неоднозначный HTTP/JSON или IN_FLIGHT требуют needs_review, а 4xx-конфигурационные ошибки — исправления владельцем. Слепое обнуление attempts/next_attempt запрещено. Триггер каждые 5 минут не создавать до одобрения уведомлений.

## 5. Браузерная форма и локальная проверка

assets/leads-config.js оставлен выключенным: существующие публичные endpoint/site key подготовлены, privacyApproved=false, версия политики ожидает утверждения; секретов в нём нет. Форма работает обычным fetch POST с JSON и credentials:omit, без no-cors. Worker разрешает только нужный Origin, Content-Type и, в TEST_ONLY, X-Mypage-Test-Key для локального отправителя. Режим неопределённого результата и успешная отправка блокируют второе нажатие даже после reset Turnstile. 429/403/400/413/503 имеют отдельные сообщения; неподтверждённый успех никогда не показывается как сохранение.

Локально: `node --test tests/*.test.mjs` и `python3 tools/check_site.py`.
Браузерные offline-сценарии: tests/form-browser.cjs с установленным Playwright и preview на 127.0.0.1:8769/mypage/. В них Turnstile и API намеренно имитируются, все внешние запросы перехватываются/блокируются. Это НЕ прохождение настоящего Turnstile и не вызов рабочих обработчиков.

Производственный Turnstile проверять только вручную в обычном Chrome. tests/live-owner-test.cjs выведен из использования после 600010. Согласованный маршрут обычный Chrome → JSON → tests/manual-owner-send.mjs описан в docs/MANUAL-FORM-TEST.md. Существующий маркер единственного POST не удалять, устаревший JSON не отправлять. Новая заявка для текущей разработки не разрешена.

## 6. Публикация — отдельное решение

После утверждения политики и backend, проверки доступов/удаления/квот и приёмки требуется отдельное одобрение merge PR #2, публикации frontend и публичного включения. Только тогда заполняются публичные endpoint/site key/version, выставляются согласованные флаги и TEST_ONLY=false. TEST_KEY при этом не публикуется. Перед изменениями обеспечить доступ к немедленному отключению Worker ENABLED/PRIVACY_APPROVED и Apps MYPAGE_ENABLED/уведомлений/ALLOW_PROBE. После отката проверить сохранение флагов; неизвестный результат сначала сверять по UUID, никогда не повторять заявку автоматически.

Пример ежедневной очистки D1 есть в backend/wrangler.toml.example; его наличие не означает установленный облачный cron. При обслуживании очередей и удалении по сроку хранения учитывать все копии и незавершённые операции. Новые ресурсы, платные услуги, публикация политики и merge этой инструкцией не выполняются.
